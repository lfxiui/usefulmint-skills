# 检查项

按顺序执行。每一项先读文件、再判断，不要为了让报告好看而虚构结论。
命令示例用项目实际的包管理器（npm、pnpm、yarn、bun 之一）。

## 1. 密钥与隐私

要查的：

- 被提交进仓库的密钥文件：`.env`、`.env.local`、`.dev.vars`、`config.json`、
  `service-account.json`、`*.pem`、`*.key`。
- 代码里写死的密钥：以 `sk-`、`sk_live_`、`ghp_`、`AKIA`、`AIza`、`xoxb-` 开头，
  或字段名含 `api_key`、`secret`、`token`、`password` 且后面跟着长字符串。
- 前后端混用：本该只放在服务端的密钥出现在 `NEXT_PUBLIC_`、`VITE_`、`PUBLIC_`
  这类会打进浏览器代码的变量里。这是最容易被利用的一类问题。
- 版本历史：密钥被删掉但提交记录里还有。用 `git log -p -- <file>` 或
  `git log -S "<片段>" --oneline` 确认。

判断：

| 情况                                       | 严重程度                 |
| ------------------------------------------ | ------------------------ |
| 服务端密钥出现在浏览器可见变量或前端代码里 | 必须修，且先作废该密钥   |
| 密钥文件已被提交进仓库                     | 必须修，且先作废该密钥   |
| 密钥只在本地未提交的文件里                 | 没问题，但确认它已被忽略 |
| 示例文件里是占位值                         | 没问题                   |

报告时不要写出密钥内容：不写开头几位、结尾几位、长度、哈希，也不做"打码展示"，
只说在哪里、是什么类型的密钥。需要指认位置时用"文件路径 + 行号"。

如果密钥已经被提交进版本历史，明确指出：删除代码不能撤销泄露，必须去服务方后台
作废并重新生成。不要替用户调用真实密钥去验证它是否有效。

## 2. 环境配置

- 比对 `.env.example` 与代码中实际读取的变量名，找出缺失项。
- 检查必需的变量是否有默认值；没有默认值又缺失的，上线后会直接报错。
- 检查部署平台的变量设置（如果用户已经部署过）是否齐全。
- 检查本地地址是否被写死在代码里：`localhost`、`127.0.0.1`、`http://` 硬编码。
  这类问题在本地正常、上线就失效。

## 3. 能不能正常构建

- 运行项目实际的构建命令，记录结果。构建失败是必须修。
- 运行类型检查或 lint（如果项目配了）。只有报错才需要处理，警告只记录。
- 如果构建产物里出现源码映射（`.map`）或体积异常大，记录为建议修。

## 4. 页面能否真的被访问到

这一项在"本地运行正常、上线就 404"的项目里最常见，单独检查：

- 启动项目（或读取入口文件），确认服务器是否真的会返回页面文件：很多 AI 生成的
  后端只处理接口路径，没有把页面目录挂上去，结果是打开首页直接 404。
- 确认静态资源（样式、脚本、图片）也在同一个服务里可访问，而不是只存在于本地磁盘。
- 确认开发时用的端口和线上期望的端口不是写死的。
- 逐个检查首页和主要入口页面能否打开，是否有空白页或报错页。
- 检查站内链接指向的路径是否存在。
- 检查图片、视频、字体等资源是否缺失（构建日志里通常有提示）。
- 检查 404 页面是否存在且不是默认的服务错误页。
- 检查表单：必填校验、提交后的提示、失败后的提示是否存在。

## 5. 手机上是否正常

- 检查页面是否有 viewport 配置（缺失时手机会按桌面宽度缩放，整页变小）（`<meta name="viewport" content="width=device-width, initial-scale=1">`）。
- 找出固定宽度（`width: 1200px` 之类）和超出屏幕的横向滚动。
- 用小窗口宽度检查文字、按钮是否溢出或被遮挡。
- 检查点击区域是否过小（按钮小于 40px 高度）。
- 检查是否有只靠悬停才显示的内容（手机上无法触发）。

## 6. 搜索与分享

- 每个页面是否有独立的标题和描述，不是所有页面共用一句。
- 是否有分享卡片配置（Open Graph：`og:title`、`og:image`）。
- 是否有 `robots.txt` 和站点地图；如果项目还在内测，确认它是否被
  `<meta name="robots" content="noindex">` 挡住了。
- 如果有统计代码，确认它不会把用户的私密数据发给第三方。

## 7. 出错时的表现

- 关键操作失败时（网络错误、接口返回错误），页面给的是白屏还是能看懂的提示。
- 接口错误是否把技术细节直接显示给用户（堆栈、SQL、服务器路径）。
- 是否有没有保护的入口：管理页面、调试页面、测试接口是否对外开放。
- 数据库或文件存储的访问规则：是否允许任何人读写（Supabase、Firebase、
  S3 这类服务要单独检查规则，默认全开放是常见问题）。

## 8. 收费与测试内容（如果项目涉及）

- 支付是否处于测试模式，正式收款前必须确认真实扣款路径。
- 代码里是否有测试账号、测试数据、示例商品没被清掉。
- 删除、退款、取消订阅这类不可逆操作是否有二次确认。
- 价格、金额是否写在代码里（可以接受，但要提醒用户改价要改代码）。

## 9. 依赖与版本

- 检查是否有已知高危漏洞：`npm audit --omit=dev`（或项目对应命令）。
- 只在有高危项时记录，低危不建议在这个阶段处理。

## 报告写法

每条问题都要能回答用户三个问题：我会看到什么现象、谁会受影响、要不要现在处理。
说不清楚的项就不要写进报告。
